---
title: "Request Block"
description: "Mutating logic for inflight headers and JSON bodies."
---

The `request` block enables you to perform lightweight transformations on the payload *before* it gets sent to the upstream provider.

## Header Operations

You can arbitrarily set or delete HTTP headers going to the upstream server.

```nginx
request {
  set_header "x-trace-id" "trace-123";
  set_header "x-foo" concat("a-", $request.model_mapped);
  
  del_header "x-remove-me";
}
```
*Note: If the same header is set multiple times, the last one wins. Deletions apply in order.*

## Model Mapping

Use `model_map` to alias or hardcode model names conditionally.

```nginx
request {
  model_map "gpt-4o-mini" "gpt4o-mini-prod";
  model_map "gpt-4o-mini" $request.model;
  
  model_map_default $request.model;
}
```
- Maps `$request.model` to `$request.model_mapped`.
- Exact match on the `from` string.
- If no matches occur, `model_map_default` dictates what `$request.model_mapped` becomes.

## Request Validation

Reject a request before it reaches the upstream. Validation runs after
`model_map` and before every JSON mutation, so a rule always sees the
parameters as the client sent them.

```nginx
request {
  req_required body "$.prompt";
  req_len      body "$.prompt" max=1500;
  req_range    body "$.n" min=1 max=9;
  req_enum     body "$.response_format" "url" "b64_json";
}
```

Each directive takes a source — `body`, `header` or `query` — followed by a
JSON path (body) or a parameter name (header, query).

| Directive | Rejects when |
| --- | --- |
| `req_required <source> <path-or-name> [allow_null=true\|false]` | the target is absent. A JSON `null` counts as absent unless `allow_null=true`. |
| `req_forbid <source> <path-or-name>` | the target is present. |
| `req_type body <jsonpath> <type>` | the field exists but is not of the given JSON type: `null`, `bool`, `number`, `integer`, `string`, `array` or `object`. Body source only. |
| `req_range <source> <path-or-name> [min=<number>] [max=<number>]` | the number falls outside the range. At least one bound is required. |
| `req_len <source> <path-or-name> [min=<int>] [max=<int>]` | the string or array length falls outside the range. At least one bound is required. |
| `req_enum <source> <path-or-name> <value>...` | the value is not one of the listed candidates. |

Behaviour worth planning around:

- **Absent targets pass every rule except `req_required`.** Use `req_required`
  to demand presence and the others to constrain a value that is there. This is
  what lets a `req_map` mode supply defaults for the fields a caller omitted.
- **`req_len` counts Unicode code points, not bytes**, so a limit expressed in
  characters holds for any script. Arrays are measured by element count; any
  other type is rejected.
- **`req_range` also accepts numeric strings**, which is what makes it usable
  against `header` and `query` sources.
- **`req_enum` compares typed JSON literals for `body`** — `"1"` and `1` are
  different candidates — while `header` and `query` values compare as strings.
- A `body` rule against a request that is not a JSON object is a failure in
  itself, not a silently skipped rule.

A failed rule returns **HTTP 400** with the failing path in `param`:

```json
{
  "error": {
    "message": "request validation failed: $.n must be between 1 and 9",
    "type": "invalid_request_error",
    "code": "request_validation_failed",
    "param": "$.n"
  }
}
```

## JSON Mutations

Apply lightweight mutations directly to the upstream JSON body.

```nginx
request {
  json_set "$.stream" true;
  json_set_if_absent "$.instructions" "";
  
  json_rename "$.max_tokens" "$.max_completion_tokens";
  json_wrap_input_text "$.input";
  json_del "$.tools";
}
```
- Supports a subset of object-path JSONPath expressions (e.g. `$.a.b.c`).
- `json_set` values support primitives (`true`, `false`, `null`, integers, strings) or expressions (like `concat(...)`).
- `json_wrap_input_text` converts a string field into an OpenAI Responses `input` message list, leaves missing or already-array values unchanged, and rejects other types.

## Structural Request Mapping

Use `req_map` to apply heavy, cross-provider schema transformations (such as converting an OpenAI JSON request into a Gemini or Anthropic JSON request).

```nginx
request { req_map <mode>; }
```

Use `after_req_map` when a request JSON mutation must run after the structural mapping step.

```nginx
request {
  req_map openai_chat_to_anthropic_messages;

  after_req_map {
    json_set "$.anthropic_version" "bedrock-2023-05-31";
    json_del_if_missing "$.tool_choice" "$.tools";
  }
}
```

- Only request JSON mutation directives are allowed inside `after_req_map`.
- If no `req_map` is configured, `after_req_map` runs after the normal request JSON operations.
